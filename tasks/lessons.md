# Lessons

记录被用户纠正后总结出的、能防止同类错误再犯的规则。

## 1. 症状驱动的猜测性修复要停手，改成完整链路审查

**发生了什么**：用户报告浮层"高亮块不跟着方向键移动"，我针对症状加了自动滚动；用户又报"出现两行同时高亮"，我又针对症状去掉了滚动动画。两次都没解决。用户第三次说"用起来还是有问题，全面审查"，一次性查出 5 个问题——真正的根因（视图里 `firstIndex(of:) ?? 0` 反查下标，`LazyVStack` 延迟求值时反查失败导致多行都算成第 0 项）从一开始就在那里，只是前两次都没去读完整条链路。

**规则**：同一个功能的 bug 报告出现**第二次**时，立刻停止针对症状打补丁，改为完整审查这条链路上的全部文件（数据采集 → 存储 → ViewModel → 视图 → 窗口事件 → 副作用出口），并且优先怀疑"兜底默认值"（`?? 0`、`?? ""`、`try?`）——它们会把本该暴露的错误变成静默的错误行为。

## 2. 不要用"反查"从子集推回父集合的下标

**规则**：视图层需要"这一项在数组里的第几个"时，绝不用 `array.firstIndex(of: item) ?? 0` 反查。要在构造数据源的同一次快照里就把下标和元素绑定在一起传下去（本项目的 `IndexedRow`）。理由：SwiftUI 的 `LazyVStack`/`LazyVGrid` 行 body 是延迟求值的，求值时父数组可能已被替换，反查失败的兜底值会让多行共用同一个下标，同时破坏高亮显示和点击/回车的目标。

## 3. 安全相关的兜底逻辑，在架构变化后要重新评估是否还有意义

**发生了什么**：`PasteSimulator` 里"粘贴 20 秒后自动清空剪贴板"最初是为保护敏感内容加的。后来隐藏内容改走 `typeDirectly`（完全不碰剪贴板），这个逻辑就只作用在"公开片段 + 剪贴板历史"这两条**本来不需要保护**的路径上，退化成"用户剪贴板莫名被清空"的纯副作用。

**规则**：为某个特定场景加的防护逻辑，在该场景改走别的代码路径之后，必须回头确认这段逻辑现在还作用在谁身上——否则它会变成只有副作用、没有收益的遗留物。

## 4. App 级事件监听器要判 `isKeyWindow`，不是 `isVisible`

**规则**：`NSEvent.addLocalMonitorForEvents` 是 App 级的，会拦截本 App 所有窗口的事件。守卫条件必须是"我是当前键盘焦点窗口"（`isKeyWindow`），只判 `isVisible` 会让浮层开着时吃掉其他窗口（如管理窗口、表单 sheet）的方向键/回车/Esc。

## 5. 键盘快捷行为不要依赖 SwiftUI 的焦点状态

**发生了什么**："选中内容按回车没反应"这个 bug 前后出现了三次。根因始终是回车走 SwiftUI `TextField` 的 `.onSubmit`，需要搜索框真正成为键盘第一响应者，而这在 `NSPanel` 首次 `makeKeyAndOrderFront` 等时序下并不保证。方向键从未出问题，因为它走窗口级 `NSEvent` 监听。

**规则**：浮层/面板类窗口里的导航与确认键（方向键、回车、Esc、Tab）统一在窗口级 `NSEvent` 监听里处理，不依赖 `@FocusState`/`.onSubmit`。

## 6. 自己写系统剪贴板时，要让自己的剪贴板监控忽略这次变化

**规则**：App 自己往 `NSPasteboard` 写内容后（比如"重新粘贴一条历史"），必须同步更新自己轮询用的 `changeCount` 基准值（本项目的 `ClipboardMonitor.suppressNextChange()`），否则监控会把自己造成的变化当成用户的新复制操作记录下来，形成"粘贴 → 被记录 → 顶到列表最前 → 下次又粘贴同一条"的自我循环。

## 7. 性能问题必须实测定位，不能猜

**发生了什么**：用户说"按快了卡顿"。我第一反应是猜"国际化引入的 `String(localized:)` bundle 查表 + 每项 `Calendar.current` 太贵"，动手把它们从循环里提出来预算一次。写了个临时基准一测——**旧实现 1.17ms、新实现 1.17ms，毫无变化**，假设当场证伪。改成在真实按键路径上插桩后，一行日志就定位了真凶：一条 39872 字符的内容让详情栏渲染耗时 11526ms，其他条目全是 15~40ms。

**规则**：性能问题一律先测再改。测量顺序是（1）先确认是普遍慢还是**特定输入**慢——用户说"每次到某一条就卡"这种线索价值极高，直接排除了普遍性能问题；（2）在真实交互路径上插桩，而不是在离线基准里测自己以为的热点。想在 SwiftUI 里量"一次交互让主线程忙了多久"，可以在事件处理开头取时间、然后 `DispatchQueue.main.async` 里取差值——异步块会排在当前 runloop 这一轮（含 SwiftUI 的视图更新+布局）之后执行。

## 8. SwiftUI 的 `Text` 没有惰性布局，长文本必须截断后再展示

**规则**：往 `Text` 里塞用户产生的、长度不可控的内容之前，先截断到展示需要的长度。`Text` 会为整个字符串做完整排版（`ScrollView` 不会让它变惰性），加上 `.textSelection(.enabled)` 还要为每个字形建立选择几何——实测 4 万字符要 11.5 秒。预览区只有几百字符可见，排剩下的纯属白烧。截断只作用于展示，粘贴/导出/搜索/去重必须仍用完整内容，并且要在界面上告知用户"预览已截断"。同理，任何对这类字符串做 O(n) 变换（换行符替换等）的地方也要先截断——因为 SwiftUI 的行 body 会被反复求值。

## 9. 需求反转时，要回头改被推翻那条逻辑的注释

**发生了什么**：我加 `ClipboardMonitor.suppressNextChange()` 时，注释写的是"防止粘贴过的条目被顶到最前面（会造成反复粘贴同一条的死循环）"。后来用户明确要求"粘贴后就是要排到最前面"——这个函数**仍然需要保留**（避免监控把自己写剪贴板误当成用户复制），但它原来的理由已经被推翻了。如果只改代码不改注释，注释就变成了会误导后来人的假信息。

**规则**：需求反转后，不只看代码要不要改，还要检查所有解释"为什么这么做"的注释是否已经与现状矛盾。留着一条理由已被推翻的注释，比没有注释更糟。
